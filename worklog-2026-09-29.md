# Worklog — 2026-09-29 · Rental renewal reminders

## What was built

A renewal reminder system for Rental deals. Nothing is scheduled and no email
is ever sent by the app itself — the radar is derived live from the deal data,
and every reminder is a user-approved `mailto:` draft sent from the user's own
mail client.

### Data model (new optional deal fields, Rental only)

- `tenancy_start` / `tenancy_end` (ISO dates). Entered on the deal form; filling
  the start auto-derives end = start + 1 year − 1 day (standard UAE term), but a
  hand-set end is never overwritten.
- `renewal_status` — `""` | `reminder_sent` | `renewed` | `not_renewed`
- `renewal_snooze_until` — hides the deal from the radar until that date
- `renewal_reminders` — `[{ date, to, subject, by }]` history of drafts
- `renewed_from_deal_id` / `renewed_to_deal_id` — the renewal chain (mirrors the
  `reversesTxnId` linking pattern)

### Core helpers (core.jsx)

`RENEWAL_WINDOW_DAYS` (90), `isoAddDays`, `isoAddYears`, `isoDaysBetween`,
`defaultTenancyEnd`, `renewalInfo(deal, today)` → `{ daysLeft, tier, status,
snoozed, inWindow }` with tiers `expired | d30 | d60 | d90 | later`,
`RENEWAL_TIER_STYLE`, `renewalReminderEmail(deal, client, settings)`,
`mailtoHref`. Only Rental deals with a valid `tenancy_end` and stage ≠ Cancelled
are tracked; `renewed`/`not_renewed` resolve a deal off the radar.

### UI

- **Deals page**: new "🔔 Renewals" filter chip (with count badge) + dropdown
  option. The Renewals view ignores the year filter on purpose and is sorted
  most-urgent first. Rows show a tier-colored chip ("renews in Nd" /
  "expired Nd ago" / "✉ reminded" / "↻ Renewed" / "Not renewed") and a
  "🔔 Renewal" action button (sales.edit).
- **Backfill nudge**: amber banner listing rental deals with no tenancy_end.
- **Renewal modal**: deal summary + editable To/Subject/Message pre-filled from
  the client record; "✉ Approve & Open in Email App" (mailto draft + stamps
  `reminder_sent` + audit `renewal_reminder_sent`), "📋 Copy Text",
  "✓ Mark Sent (no email)"; outcome actions "✔ Mark Renewed" (with a checkbox,
  default on, that clones the deal into the next tenancy year — new id, stage
  Lead, back-to-back tenancy dates, collection state reset, linked both ways;
  audit `deal_renewed`), "✕ Not Renewed" (confirm; audit `deal_not_renewed`),
  and Snooze-until-date (audit `renewal_snoozed`).
- **Dashboard**: new Management Alert "N rental tenancies due for renewal
  within 90 days" (critical when any already expired) with the deal drill-down
  table; its button presets the deals filter to Renewals via
  `ls_set("deals_filter", ...)` before navigating (works because pages remount
  on navigation).
- **Deal Card**: tenancy period line under Deal economics.

### Tests

`tests/renewal.test.js` (node, 0 deps, house style — canonical rules mirrored
from core.jsx): date arithmetic incl. leap-day term, radar eligibility, tier
boundaries at 0/30/31/60/61/90/91 days, status/snooze behaviour, renewal chain
dates, mailto encoding. 34 assertions, all passing; commission suite still green.

## Deliberate choices

- **mailto over a sending service**: keeps the no-backend/no-CDN architecture;
  approval is literally the user pressing Send. Upgrade path discussed: Firebase
  "Trigger Email" extension writing to a `mail` collection (needs Blaze) —
  the modal UX would not change.
- A collected rental still appears on the radar (the tenancy still expires and
  renewal = next year's commission).
- Reminder history is stored on the deal, count-only in the audit log.
