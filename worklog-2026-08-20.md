## 2. The one that mattered — a deposit read as commission collected

`dealCollection` (`core.jsx`) sums bank/cash **debits** on any transaction linked to a
deal. `postClientFunds` stamps `deal_id` on the transaction *and* both lines, and debits
the bank. So a deposit registered as commission collected the moment it arrived.

Worked example — a deal with AED 121,000 of gross commission, AED 200,000 deposit:

| | Before | After |
|---|---|---|
| Collected on the deal, at receipt | **200,000.00** | 0.00 |
| Remaining commission | **0.00 — reads as fully paid** | 121,000.00 |
| After refunding the deposit in full | **still 200,000.00** | 0.00 |

The refund never undid it, because a refund is a **credit** and the sum only counts
debits. A deal that took a deposit and gave it straight back stayed marked as paid
permanently.

Blast radius was all three `dealCollection` consumers: the Deals page (`pages.jsx:2434`),
the deal detail installment list (`pages.jsx:1854`), and the dashboard installment alert
(`pages.jsx:442`).

**Fix:** `dealCollection` now skips `received` / `paid` client-funds movements entirely,
and counts the `earned` entry's 2230 debit instead. That entry carries no cash line — the
money is already in the bank — but it is the exact moment the money stops being the
client's, so it is the right thing to call a collection.

**This is the rule to remember:** any new code asking "what has this deal collected?"
must not go back to summing raw bank debits.

### Why this was the everyday case, not an edge case

Owner input today: **deposits are normally not used on buy/sell deals — the common flow
is receive, hold, refund in full.** Deducting the office commission from a deposit is
rare. So the broken path was the one that runs most often, and the rare path (close-out)
is the one worth keeping correct precisely because a wrong number there would sit
unnoticed for a long time.

## 3. The other four findings

**A. Close-out could recognise a commission twice.** `depositCloseoutPlan` took the deal's
full commission with no regard for revenue already booked against it. Closing a deposit on
a deal already collected by Sale Receipt or invoice would have posted the commission a
second time. It now takes a third argument — what the deal already collected elsewhere —
and nets it off. The modal shows an *Already collected on this deal* line when it bites.

**B. A latent trap this exposed.** The "use the deal's own stored net" shortcut was keyed
on `applied === commissionGross`. Correct while `commissionGross` was always the deal's
full commission — but once it can be net of prior collection, a partly-collected deal
would have produced a **negative VAT**. Now keyed on `applied === fullCommission`. This
was pre-existing dormant code that only became reachable because of fix A; it is pinned
by a test.

**C. The posted split could differ from the approved one.** The modal showed a net/VAT
split from `expected_commission_net`; the posting re-derived `gross ÷ 1.05`. These agree
until a deal's stored net drifts — which is exactly what `commissionMismatch` exists to
flag — and under INCLUSIVE terms a drifted net meant the user approved one split and the
ledger recorded another. `postClientFundsEarned` now takes an optional `netCents` and the
close-out passes the approved figure. Out-of-range values are refused.

**D. `customer_id` was half-wired.** Set in form state and passed on receipt, but no UI
field populated it and neither payout path forwarded it. Adding a customer picker later
would have split one client into two subledger rows — deposit under `customer_id`, refund
under `party:<name>`. Added the picker and threaded the id through both payout calls.

**E. Receipt numbering invented numbers on failure.** The catch minted
`parseInt(Date.now().slice(-5))`, which can collide with an issued number or jump the
series — in a comment block insisting the series must be gapless. It now throws; the
caller already toasts the failure, and no receipt document is written without a real
number.

## 4. Settled deposits kept as history

Raised during review that a fully refunded deposit vanished from the Open Deposits table
entirely, surviving only in the flat Deposits Received list. Owner asked for it to remain
as history.

The table is now *Deposits — by client / deal* with an "N open, N settled" count and a
**Show N settled** toggle. Settled rows render greyed below a divider, newest first,
carrying a **Refunded** or **Closed out** badge where the held amount would be — so a zero
can never be misread as still holding something — with their Received / Applied / Refunded
figures intact and no action buttons.

History is derived from the transactions themselves, not a separate record, so it cannot
be lost. A party whose balance goes **negative** (refunded more than they paid) stays in
the open list rather than dropping into history, because that needs attention.

   origin main`.
2. **First load auto-creates account 2230** via the `client_funds_acct_v1` migration —
   a one-time write to the live chart of accounts. Worth confirming it appeared as a
   Liability, not flagged bank or cash.
3. **Two places still equate `txnType === "SR"` with collection**, so a deal closed out
   from a deposit looks uncollected to them: `pages.jsx:427` (the dashboard "Commission
   Earned with no receipt recorded" alert will keep nagging) and `pages.jsx:4457` (deal
   P&L cash-in reads zero). Both are the same one-line shape as the `dealCollection` fix.
4. **`validateDealRevenueReceipt` has the same gap** (`core.jsx`, SR-only) but is not
   called anywhere in the app — dead code for now, worth either wiring up or deleting.
5. **The deal card no longer shows a deposit at all.** Correct — it is not collection —
   but a deposit sitting against a deal is exactly what you want to know when deciding
   how to collect. Offered a separate "held on deposit (not collected)" line, not built.
6. **Button order.** In the deposits table *Close deposit* renders first as the visually
   equal option, with *Refund all* beside it. Given refund-in-full is the norm and
   close-out is the rare irreversible one that recognises revenue and charges VAT, that is
   backwards. Offered, not done.
7. **Close-out is two postings and is not atomic.** If the refund fails after the
   commission is recognised, the toast says exactly that and names both figures — but the
   books are left mid-way and the refund must be posted manually.
8. **The RBAC permissions screen doesn't list Client Deposits.** `core.jsx` ~217 carries
   a human-readable page list per permission group; the new page is absent, so the screen
   under-describes what `sales.read` now grants. Cosmetic.
9. **Receipt numbers sort wrong past RCP-99999.** `depPad` stops zero-padding beyond five
   digits, so string sorting breaks at 100,000 receipts. Noted, not worth fixing.

## Net effect

The deposits feature is committed and deployed after a review that found one bug hitting
the everyday path — every deposit linked to a deal was being counted as commission
collected, and a refund could never take it back — plus a double-recognition hole and a
split the ledger could record differently from what the user approved. All fixed and
pinned by tests.

What is left is mostly small and known: two SR-only spots now out of step with the new
collection rule, two UI offers not taken up, and the fact that none of this has been
opened in a browser. The last one is the only one that could be expensive.
