## 2. Browser verification of the 2026-07-27 VAT work

The VAT-inclusive mode and the deal↔invoice guards had only ever been verified by
transpile and unit tests. Today they were driven in a real browser.

### How the browser test avoided production

Logging into the live app needs an access code, and driving the live app would have
written to production financial data. Neither was acceptable for a verification pass,
so the app's own offline path was used instead:

- `pages.jsx:6032` auto-logs in as **admin** when `db` is undefined. The Firestore
  listener effect calls `db.collection(...)` unguarded, so a *mock* `db` is needed
  rather than none.
- A local static server serves the **real repo unmodified**, substituting only
  `nasama-accounting-v2.firebase.js` for an in-memory Firestore, seeded from a
  read-only snapshot of live data (113 deals, 869 transactions, 28 invoices, 56
  accounts). Real React, real vendored Babel, real UI code.
- Every write is captured in-tab on `window.__WRITES__` instead of leaving the
  machine, so a test can assert on the exact payload. There is no Firebase SDK in
  the harness at all — a write *cannot* reach production.
- The seed deliberately **skips `authorized_users`** (it holds access codes); the
  harness synthesizes its own admin.

Live-data contact was three read-only anonymous-auth REST sessions (the same path
`tools/phase0-attribution.js` uses). They create three anonymous Firebase Auth users,
which are harmless and safe to delete.

### Bugs found and fixed

**A. The printable Deal Card stated the wrong VAT basis.**
`pages.jsx:2140` hardcoded `"Yes — 5% added on invoice"`. Its sibling at
`pages.jsx:1937` was made mode-aware on 2026-07-27; the dossier was missed. TVI-126's
**confidential dossier — a document handed to clients and management — was
contradicting the invoice raised from the same deal.** Now mirrors line 1937.

**B. The fix-the-deal confirmation asserted the wrong basis.**
`invoices.jsx:1266` ended `"The 5% VAT is added on top on the invoice."`
unconditionally. That text appears at the exact moment the user approves a write to a
deal, so under VAT-inclusive terms it misstated what was about to happen. It now names
the actual mode, and under inclusive terms quotes the resulting all-in total:

> Set The View Island's expected commission to AED 115,238.10?
> That is 2,420,000.00 × 5% with the 5% VAT taken out of it, so the invoice still
> totals AED 121,000.00 including VAT.

Both are the same class of miss: the 2026-07-27 change made the *calculations*
mode-aware but left mode-blind **copy** behind in two places that a user actually
reads.

## 4. Unpaid accruals now read red with an `UNPAID` tag (new feature)

An accrual (`AC`) recognises an expense before the cash goes out: DR expense /
CR 2210 Accrued Expenses Payable. Nothing outside the Future Expenses page marked
them as different from a settled expense, so money still owed looked exactly like
money already paid.

### The decision that shaped it
An accrual stays in the ledger for good, but it is only *unpaid* until a settlement
clears the payable. Asked the owner whether the red/`UNPAID` treatment should be
permanent or lifecycle-aware; **the ruling was lifecycle-aware**: red only while
outstanding, then a quiet green `SETTLED`. All 8 current accruals are unpaid, so both
options looked identical today — the difference only appears after the first
settlement, when the permanent version would have labelled a **paid** expense
"Unpaid" on a financial report.

### Where it shows
| Surface | Treatment |
|---|---|
| Journal Entries | red type badge + `UNPAID` pill + red bold amount |
| Dashboard → Recent Transactions | red description + `UNPAID` pill + red amount |
| Future Expenses | `🧾 Accrued` badge turned red, `UNPAID` pill, red title |
| General Ledger (screen) | red row + `UNPAID` pill, under **both** the expense account and 2210 |
| General Ledger (printed PDF) | red row **plus a literal `[UNPAID]` marker** |
| Excel export | new `Accrual` column carrying the status as text |

The printed ledger carries a word as well as a colour deliberately — a mono printout
would otherwise lose the distinction entirely.

### How it is wired
One block in `core.jsx` is the only place the rule lives: `isAccrualTxn`,
`accrualStatus`, `ACCRUAL_STATUS`, `accrualColor`, `<AccrualTag>` and
`accrualStatusLabel` (the plain-text form for exports). Every screen and report reads
those, so the flag **cannot say one thing on the Journal and another on a report**.
`accrualStatus` returns `unpaid` / `settled` / `reversed` / `void`, matching a
settlement to its accrual on `planned_expense_id` and honouring the reversal
contra-entry model.

**The trap worth recording:** the settlement transaction is tagged
`accrual-settlement`, which *contains* the string `accrual`. A naive substring test
would have classified every settlement as an accrual — and since settlements are the
thing that clears the flag, accruals would have appeared to settle themselves. Tags
are therefore compared as **whole words**, pinned by a test.

### Two pre-existing gaps closed on the way
1. **`AC` was not in `TXN_TYPES` at all.** All 8 accruals rendered as a bare "AC"
   across the app, and the Journal's type filter had no way to select them.
2. **Future Expenses coloured off "is accrued" rather than "is still owed"**, so a
   settled item would have kept reading red. Now driven by the shared status.

### Verification

- Nothing regressed: the 27 + 47 browser assertions from §2, plus 458 commission and
