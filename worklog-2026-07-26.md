## 1. Employees — per-person financial subledger (admin-only)

**Commit:** `90b829b` · 8 files, +1,947 / −2

### Why
Nothing in the system answered *"what does this person cost us, what did they
bring in, and were they actually paid?"* The Performance page already ranked
brokers by commission **generated**, but never by what they **cost** — so a
broker who bills a lot while costing more was indistinguishable from one running
a healthy margin. Office staff were worse off still: an admin or accountant
existed only as free-text `counterparty` on a payment voucher, so they were
invisible to every screen in the app.

### Phase 0 first — measure before building
A read-only diagnostic (`tools/phase0-attribution.js`, zero deps, Firestore REST
+ anonymous auth) was run against live data — 17 brokers, 113 deals, 830
transactions — before a line of UI was written. Two findings changed the plan:

**Broker identity is clean.** All **113 of 113** deals have `broker_id` matching
`broker_name`; grouping by ID and by name give identical answers. The mismatches
visible in the seed data in `core.jsx` never reached live data, and the duplicate
Teryaki record had already been merged. **The planned identity migration was
cancelled.**

**But 95.7% of payroll is attributed to nobody.** Of AED 2,502,854.73 of GL
movement on 5000/5010/5020/5030/5040/5500/5510, only **AED 108,153.05** carried a
person tag. Cause: only `postBrokerPayment` (`BP`) writes `broker_id`, and that
flow is recent — bank-statement imports and manual `JV`/`PV` entries tag nobody.
Built naively, the module would have been ~96% empty.

The payee names *are* in the bank narrations, so ~71% (AED 1.69M) proved
script-recoverable. The remainder is the AED 332,008 own-account question below.

### What changed
New file **`nasama-accounting-v2.employees.jsx`** (~640 lines) with a pure
`buildEmployeeLedger()` engine and five tabs:

- **Roster** — headcount cards with a pay-basis badge derived from *actual GL
  activity* rather than a settings field (`Commission-only` / `Salary + Commission`
  / …), plus RERA expiry countdown.
- **Employee 360** — the dossier: every bank transaction, cost split by nature
  (salary / commission / override / incentive / visa-licensing), revenue
  generated, net contribution, margin, payback bar, and collected deals with no
  broker payment recorded. Non-revenue staff read *"Support cost — no direct
  revenue"* instead of a meaningless 0% margin.
- **Payroll Register** — person × account matrix, closed with a **control total
  that reconciles to the general ledger**. This is what makes it a subledger
  rather than a dashboard.
- **Contribution** — ranked by net contribution, not revenue.
- **Exceptions** — unattributed payroll, own-account payments, unconfirmed
  provisional matches, RERA expiries, negative payroll.

**Runtime attribution.** Because the attribution migration has not run yet, the
module applies the matcher live and labels every recovered line **`provisional`**
in the UI — visibly separated from tagged ground truth, and never presented as
fact.

**Consonant-skeleton name matching, not edit distance.** Banks transliterate
Arabic names inconsistently: `FOAD`/`FOUAD` for *Faoud*, `TARIQ`/`TAREQ` for
*Tarek*, `AHMED` for *Ahmad*, `KHAIRI` for *Khiari*. An edit-distance matcher was
tried first and **silently dropped Faoud Dada entirely** — the largest broker,
AED 420k of payments. Skeleton matching (drop vowels after the first letter,
`Q`/`C`→`K`, collapse doubles) handles all of these. Confirmed variants live in a
per-person `aliases[]` list rather than in a looser algorithm, because loosening
trades false negatives for false positives on real money.

**Provisional roster.** With the `employees` collection empty the page derives a
roster in memory from `brokers` plus the confirmed non-broker staff, so it is
useful immediately. A "Create employee records" button persists it — nothing is
written until that click.

**Visibility: full admin only, implemented by omission.** `employees` is
deliberately absent from `PAGE_ACCESS_BRIDGE` *and* from the legacy role map, so
`canAccessPage()` returns `true` for admin on its first line and falls through to
`false` for everyone else. No new permission key, no role migration. Worth
recording why the obvious approach was wrong: the **secretary** template already
grants `accounting.read`, so reusing that key would have exposed payroll to
secretaries; and a purpose-built `accounting.payroll` key would not have reached
already-saved `security_roles` docs, which are seeded only when the collection is
empty — an accountant would have been locked out until an admin re-saved the role.

Wiring (14 lines total across 3 existing files): `index.html` script tag before
`pages.jsx`; NAV `PEOPLE` section in `core.jsx`; and in `pages.jsx` the
`employees` state, Firestore listener (`total` 10→11), `setEmployeesFS`, `shared`,
the `renderPage` case, and a `SidebarIcon` glyph.

### Bug caught during verification
The first version tested for "paid to a Nasama account" **before** matching the
payee name. But Nasama's own account appears in outgoing narrations as the
**sender** —
`Acct to Acct FUND TRANSFER - 019101846426 - NISADI SANDUNIKA FERNANDO` — so real
payments to real people were being swallowed into the own-account bucket: AED
548k instead of AED 332k, and one employee's salary cut from AED 22,250 to AED
2,250.

Notably, **the control total tied either way** — so a reconciliation check alone
would have passed this silently. It was caught only by comparing the in-app
engine against the standalone diagnostic. Order is now
**tagged → provisional → own-account → unattributed**, pinned by a regression test.

### Verification
- All three changed `.jsx` files transform cleanly under the vendored Babel
  7.29.7 (still pinned — Babel 8's automatic JSX runtime blanks the app).
- `node tests/employees.test.js` — **37 assertions pass**: skeleton matching,
  ambiguity refusal, control total, resolution order, reversals, revenue side,
  period filter, roster derivation. Zero dependencies, same style as
  `tests/commission.test.js`.
- `node tests/commission.test.js` — still **170 pass**, nothing regressed.
- Engine run against live Firestore: control total **ties at AED 0.00**
  difference, and the own-account bucket reproduces the standalone tool's
  **AED 332,008 / 13 lines** exactly.

### Notes
- Module GL scope adds **5420 Recruitment** and **5430 Trakheesi** as cost-to-employ,
  so its total (AED 2,605,535.07) runs AED 102,680.34 above the diagnostic tool's
  payroll-only figure. Intentional.
- Reversals render as a `reversal` badge rather than negative salary — six people
  carry negative 5010 lines, and summing them blindly would misstate their margins.
- Every figure derives from the general ledger. `base_salary` is stored for
  planning only and is never used in a reported number.

## Net effect
The business can now see, per person, what they generated, what they cost, and
what they are owed — with a register that reconciles to the general ledger. The
data problems that would have made those numbers wrong were found and quantified
*before* the module was built, rather than discovered through a misleading report
later.

Committed and pushed to `origin/main`; live.
