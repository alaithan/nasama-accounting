## 1. Self-host all vendor libraries — remove CDN runtime dependency

**Commit:** `3112c87` · **Branch:** `self-host-vendor-libs`

### Why
The app loaded 10 libraries + a pdf.js worker from unpkg / cdnjs / gstatic at
runtime. Any CDN outage or silent version bump could break the whole accounting
system — exactly what happened on 2026-06-17 when unpkg moved Babel 7.x → 8.0.1
and blanked the app. It also meant every visit re-downloaded and re-transpiled
from third-party servers.

### What changed
- Created `vendor/` and downloaded 11 byte-identical files (same pinned versions):
  react 18.3.1, react-dom 18.3.1, @babel/standalone 7.29.7, firebase
  app/firestore/auth 10.11.0, html2canvas 1.4.1, jsPDF 2.5.1, xlsx 0.18.5,
  pdf.js 3.11.174, and the pdf.js **worker** 3.11.174.
- `index.html` — 10 `<script src>` tags repointed from CDNs to `./vendor/...`
  (same load order, Babel comment/pin preserved).
- `nasama-accounting-v2.reconcile.jsx` — `RECON_PDF_WORKER` repointed to the
  local `./vendor/pdf.worker-3.11.174.min.js`.

### Verification
- Every downloaded file checked for size + that it wasn't an HTML error page;
  Babel confirmed still 7.29.7 (not 8.x).
- Cross-checked: zero remaining CDN URLs, every `./vendor/` ref exists on disk.
- Served locally, user confirmed Dashboard, Invoices, and Bank Reconciliation
  (PDF upload — the one worker-dependent feature) all work.
- Post-deploy: live site references `./vendor/`, all files return HTTP 200.

### Notes / decisions
- **No build step / bundler / npm** was added — deliberate, per
  `SELF-HOST-VENDOR-PROMPT.md`. App stays a plain static site.
- Firebase still talks to Google at runtime — that's the database connection,
  not a library load, and is unaffected.
- Repo grew ~5 MB (the point — libraries frozen in the repo).
- Fully reversible: `git revert 3112c87`.

## 2. Simplify Deals-Report commission + add math tests

**Commit:** `f40442a` · **Branch:** `commission-diagnostic`

### Why
`DealsReportDoc.rowCommission` used a fragile 10-line heuristic that *guessed*
whether a Secondary deal's stored `expected_commission_net` was "buyer-only" by
recomputing the buyer figure and comparing within 1 cent. This inferred meaning
from data values — the kind of thing that silently mis-states commission on a
confidential management report.

### Investigation (read-only)
- `expected_commission_net` is already the single canonical figure everywhere;
  only `rowCommission` re-derived it.
- The deal editor stores Secondary net as `buyer + seller − discount` (field
  auto-computed & disabled), and imports store the collected net directly.
- All 19 imported Secondary deals have **no** `seller_commission` field → the
  guess branch can never fire for them.
- Conclusion: the heuristic was effectively dead code, and a blanket data
  migration would be risky and unnecessary.

### Approach — diagnose before migrating
Rather than write to live financial data speculatively, built a **read-only
diagnostic** (temporary admin button) that scanned every deal and reported any
where the heuristic value differed from the stored net.

- **Result across all 109 live deals: 0 affected.** (Node pre-check against the
  64 imports also showed 0.)
- The 3 "Secondary net ≠ recompute" rows were the expected case where an
  imported discount is baked into the net (discount lives in `notes` text) —
  correct as-is, not errors.

### What changed
- `rowCommission` collapsed to `d => d.expected_commission_net || 0`
  (zero behaviour change — proven by the diagnostic).
- **No data migration** — proven unnecessary; live records untouched.
- Added `tests/commission.test.js`: zero-dependency, run with
  `node tests/commission.test.js`. 170 assertions covering single-side +
  Secondary commission, VAT (5%), and invariants over the real 64-deal import.
  It caught 3 harmless sub-dirham rounding quirks in the Off-Plan imports (now
  tolerated within AED 1).
- The temporary diagnostic button/modal/helper were **removed** after they did
  their job — toolbar is clean again.

### Verification
- File parses cleanly via the vendored Babel (checked after each edit).
- Tests: 170/170 pass.
- Final diff to `pages.jsx` is only the `rowCommission` simplification.
- Post-deploy: live site serves the simplified function.

### ⭐ Lead Source / CAC tracking (agreed — do in a future session)
**Goal:** know which marketing channel each deal came from, so we can compute
cost-per-deal (Customer Acquisition Cost) per channel and reallocate spend.

**What it needs:**
1. **New field on the deal form** — `lead_source` (dropdown), e.g.
   Bayut · Property Finder · Referral · Walk-in · Social/Instagram · Other.
   Add to `DealForm` and the `empty` deal template; store on the deal doc.
   (Optional: a small master-list CRUD like brokers/developers so the list is
   editable, rather than a hard-coded enum.)
2. **Backfill** existing deals — leave blank / "Unknown"; no migration needed,
   the field just reads empty for historical deals.
3. **CAC report** — group marketing expenses by channel (the expense categories
   already exist: Property Finder, Bayut, Social Media) and divide by the number
   of deals per `lead_source` in the period:
   `CAC(channel) = marketing_spend(channel) / deals_count(channel)`.
   Surface as a table/section (Performance page) and/or a dashboard tile.
   Decision it drives: "AED 50k on Bayut → 2 deals vs AED 10k on Instagram →
   5 deals; shift budget to Instagram."

**Notes:** this is the one roadmap item requiring NEW data capture, so its value
only starts accruing after the field exists and deals are tagged going forward.
Historical CAC will be partial until enough tagged deals accumulate.
